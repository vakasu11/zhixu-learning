# 数据结构全章代码复习库设计规格

## 1. 目标

将现有的 21 章、63 个代码专题扩展为一套可验证的完整代码复习库。课程范围继续以《数据结构、算法与应用（C++语言描述·第2版）》对应的 21 章、146 个知识点为主线。凡是能够形成有学习价值的程序、数据结构操作、算法骨架或性能实验的知识点，都提供原创 C++ 实现；纯理论内容不制造无意义代码，而是明确关联到能够验证该理论的实现或实验。

完成后，学习者能够按章节快速找到代码，理解每段代码解决什么问题、依赖什么知识、如何执行、复杂度如何、哪些地方容易写错，并能在手机端舒适地阅读和复制。

## 2. 范围

### 2.1 包含

- 教材 21 章全部纳入覆盖清单。
- `lib/study-content.ts` 中数据结构课程的 146 个知识点全部获得唯一覆盖状态。
- 所有可编程知识点均对应至少一个原创 C++ 代码专题。
- 每个专题包含用途、前置知识、实现步骤、复杂度、核心不变量、易错点、关联知识点和代码。
- 代码按章节拆分维护，并在构建时汇总为网站使用的统一列表。
- 网站提供章节导航、章内类别导航、关键词搜索、优先级筛选、折叠阅读和复制代码。
- 桌面端与手机端均可使用；手机端默认保持紧凑和折叠。
- 使用自动化检查验证章节、知识点、代码元数据与标识符的完整性。

### 2.2 不包含

- 不加入在线编译、在线运行、判题、代码执行后端或安全沙箱。
- 不逐字复制教材、课件或第三方仓库中的源代码。
- 不公开学校网盘的深层私有链接或未获授权的学习资料。
- 不扩展到数据结构课程之外的其他四门课程。
- 不建立大规模练习题库；本阶段仍以知识解析和代码复习为主。

## 3. “全部代码”的判定规则

146 个知识点中的每一项必须被归入以下一种状态，并且只能有一种主状态：

1. `code`：该知识点具有独立的数据结构、算法、操作或应用实现，必须关联至少一个代码专题。
2. `experiment`：该知识点主要通过性能测量或对比实验理解，必须关联至少一个实验代码专题。
3. `related`：该知识点本身是定义、性质或分析方法，没有独立代码，但必须关联到最能体现它的代码专题。
4. `theory`：该知识点是纯理论说明，不适合独立或关联代码；必须写明无代码原因。

覆盖完成的判定不是达到一个预设代码数量，而是 146 个知识点全部进入覆盖清单，且所有 `code` 和 `experiment` 项都有有效代码引用。最终专题数量由实际映射结果决定，预计约 100 至 130 个。

## 4. 内容模型

### 4.1 代码专题

每个代码专题使用统一结构：

```ts
type CodeReviewItem = {
  id: string;
  chapter: number;
  category: string;
  title: string;
  priority: "必会" | "重点理解" | "拓展";
  topicIds: string[];
  prerequisites: string[];
  purpose: string;
  steps: string[];
  complexity: string;
  invariant: string;
  pitfalls: string[];
  code: string;
};
```

约束：

- `id` 全局唯一，并使用稳定的英文短横线格式。
- `chapter` 必须为 1 至 21。
- `topicIds` 至少包含一个覆盖清单中的知识点标识符。
- `steps` 至少包含两个按执行顺序排列的实现步骤。
- `code` 是原创、适合复习的 C++17 实现；包含核心类型和函数，不依赖网站运行环境。
- 多个知识点可以关联同一个专题，一个知识点也可以由多个专题共同解释。

### 4.2 知识点覆盖记录

```ts
type TopicCoverage = {
  topicId: string;
  chapter: number;
  topic: string;
  status: "code" | "experiment" | "related" | "theory";
  codeIds: string[];
  reason?: string;
};
```

约束：

- 146 个课程知识点各有且仅有一条记录。
- `code`、`experiment` 和 `related` 的 `codeIds` 不得为空，并且每个标识符必须指向真实代码专题。
- `theory` 的 `codeIds` 必须为空，`reason` 必须解释为何没有有意义的代码实现。

## 5. 文件结构

将现有单个超长数据文件拆分为小型、独立、可审查模块：

```text
lib/data-structure-code/
  types.ts
  coverage.ts
  index.ts
  chapters/
    chapter-01.ts
    chapter-02.ts
    ...
    chapter-21.ts
scripts/
  validate-data-structure-code.mjs
```

- `types.ts` 定义内容模型。
- 每个章节文件只负责本章专题。
- `coverage.ts` 保存 146 个知识点的覆盖状态和关联。
- `index.ts` 汇总、排序并导出现有 UI 所需的统一接口，避免组件了解文件拆分细节。
- 原 `lib/data-structure-code-library.ts` 在迁移完成后改为兼容导出或删除；不得同时保留两份真实数据源。
- 校验脚本负责结构、覆盖与引用完整性检查。

## 6. 各章内容边界

代码复习库按现有课程目录扩充，重点包括但不限于：

- 第 1-4 章：C++ 基础、递归、动态内存、异常、STL、操作计数、渐近增长与性能实验。
- 第 5-7 章：数组线性表、链表及其变体、排序应用、并查集、数组映射、特殊矩阵与稀疏矩阵。
- 第 8-10 章：数组栈、链式栈、栈应用、循环与链式队列、队列应用、跳表、散列和 LZW。
- 第 11-15 章：二叉树表示与遍历、堆与左高树、霍夫曼、竞赛树、BST、索引 BST、AVL、红黑树、分裂树和 B 树。
- 第 16-17 章：图表示、遍历、路径、连通分量、生成树，以及贪婪法的装载、覆盖、最短路径和最小生成树应用。
- 第 18-21 章：分治、动态规划、回溯和分支定界的教材应用，包括排序、选择、最近点对、背包、矩阵链、最短路径、最大完备子图、旅行商和电路板排列。

同一算法在不同章节使用不同设计方法解决时，保留不同专题，并明确比较状态表示、搜索顺序、剪枝条件和复杂度。

## 7. 页面设计

继续使用现有“代码复习库”页签，不改变课程主导航。

### 7.1 顶部概览

- 显示实际代码专题总数、21 章和 146 个知识点覆盖完成度。
- 保留关键词搜索和优先级筛选。
- 章节按钮显示本章代码数量。

### 7.2 章内导航

- 选择章节后显示本章类别，例如“基础实现”“核心操作”“典型应用”“性能实验”。
- 类别来自内容数据，不在组件中硬编码。
- 默认显示全部类别，允许一键收窄。

### 7.3 代码卡片

- 卡片标题区显示章节、类别和优先级。
- 摘要区显示用途与前置知识。
- 展开后依次显示实现步骤、复杂度、不变量、代码和易错点。
- 代码区提供复制按钮。
- 手机端默认折叠详情；桌面端也不一次性展开全部代码，避免长页面和过多渲染。
- 搜索结果无匹配时提供清除筛选操作。

## 8. 数据流

1. 章节模块导出 `CodeReviewItem[]`。
2. `index.ts` 合并 21 个章节，按章节、类别和标题稳定排序。
3. 覆盖清单引用代码专题 `id`。
4. 校验脚本在构建前检查数据一致性。
5. 页面组件读取汇总列表和覆盖统计，执行客户端筛选与折叠展示。

所有内容保持静态，不请求代码执行服务，不上传学习者代码，也不产生新的数据库依赖。

## 9. 内容编写标准

- 所有实现使用 C++17。
- 每段代码包含自身语法检查所需的头文件、类型声明和辅助函数；可以没有 `main`，但不得依赖另一张卡片中的隐藏声明。
- 优先使用清楚、适合教学的写法，而不是竞赛式极端压缩代码。
- 命名表达结构含义，避免单字母名称，循环下标除外。
- 明确边界条件、空结构、单元素、重复关键字、无解和溢出风险。
- 复杂度区分最好、平均、最坏或均摊情况，只写适用的维度。
- 不变量描述代码在循环、递归或结构更新过程中必须保持的事实。
- 易错点必须针对该实现，不能使用所有专题都一样的泛化文案。
- 可复用的数据结构可以在专题中给出完整核心类；应用专题可以使用标准库容器，但要说明容器承担的角色。
- 不以第三方高星仓库为代码来源；可借鉴通用算法知识，但实现和讲解均重新组织。

## 10. 校验与测试

### 10.1 内容校验

自动化脚本必须检查：

- 正好存在 21 个章节模块，并且每章至少有一个代码专题。
- 所有专题 `id` 唯一，章节范围合法，必填字段非空。
- 所有 `topicIds` 都存在于覆盖清单。
- 覆盖清单正好包含课程目录中的 146 个知识点，且无重复、无遗漏。
- `code` 和 `experiment` 状态至少关联一个有效代码专题。
- `related` 状态至少关联一个有效代码专题。
- `theory` 状态没有代码引用且包含原因。
- 所有覆盖关系双向一致：专题引用的知识点存在，覆盖记录引用的专题也存在。

### 10.2 代码语法检查

- 将每个专题的代码写入临时 `.cpp` 文件。
- 在本机存在 C++ 编译器时，逐个执行 C++17 语法检查。
- 若某段代码设计为类或函数库而没有 `main`，使用仅语法检查模式，不要求链接。
- 无编译器时，内容结构检查仍必须通过，并在交付说明中明确未执行编译器验证。

### 10.3 应用验证

- GitHub Pages 生产构建必须成功。
- 桌面宽度和 390px 手机宽度检查章节导航、类别导航、折叠、搜索、筛选和复制按钮。
- 浏览器控制台不得出现由本次改动引入的错误。
- 若完整 TypeScript 检查仍显示项目已有错误，必须区分既有问题和本次新增问题，不能将静态构建通过表述为全量类型检查通过。

## 11. 错误处理

- 数据校验失败时，脚本输出具体章节、知识点或代码 `id` 并以非零状态结束。
- 页面遇到空筛选结果时显示可恢复的空状态，不显示空白页面。
- 复制失败时显示失败提示，成功时显示已复制提示。
- 某个章节数据为空属于构建错误，不允许仅在运行时隐藏。

## 12. 性能与移动端约束

- 不引入新的运行时依赖或后端服务。
- 代码详情按用户操作展开，避免初始页面创建上百个大型代码块。
- 保持章节与类别导航横向滚动，不压缩成难以点击的小按钮。
- 代码区域允许水平滚动，正文不得导致整个页面横向溢出。
- 若扩充后的单个 JavaScript 包显著增大，按章节执行静态懒加载；只有实际构建数据证明需要时才增加该复杂度。

## 13. 验收标准

只有同时满足以下条件才算完成：

1. 21 章均有独立章节模块和有效代码内容。
2. 146 个知识点全部出现在覆盖清单中，无重复、无遗漏。
3. 所有可编程或实验型知识点均关联原创 C++ 代码。
4. 所有纯理论项都有明确说明，不以无意义代码凑数。
5. 网站支持章节、类别、关键词和优先级浏览，并在手机端可用。
6. 内容校验脚本通过，生产构建通过。
7. 未增加在线编译器、代码执行后端或学习者代码上传。
8. 公网 GitHub Pages 加载新版，并能验证新专题数量与覆盖统计。

## 14. 发布策略

实现期间按内容模型、章节内容、UI 和验证四个阶段推进。全部本地检查通过后统一提交并推送到 GitHub Pages。发布后直接读取线上 HTML、脚本与样式资源，确认新覆盖统计和页面文案已生效。
